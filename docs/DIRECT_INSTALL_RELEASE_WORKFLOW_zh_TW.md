# MSH 直接安裝與往後發佈流程

本流程採用 Windows 安裝版。一般使用者不需要 Git、Python、Conda 或專案原始碼。
MSH 提供功能；模型、影像、標註、訓練資料及結果由使用者自行保存，均不隨安裝版提供。

## 現行流程（2026-11-18）

現行需求為 NVIDIA GPU 優先、CPU 備用、線上安裝先行、完整離線交付後續處理。
目前應用程式來源、建置、安裝附件與更新資訊統一在 Public `MSH-Releases`。舊 Private `Microscope-Scanner-Helper_MSH` 保留研究歷史與資料；新庫只承接目前乾淨的應用程式快照，不帶舊 `.git`。
新來源副本為 `0.1.5-dev.5`，採同庫短效內建授權；遷移前的 dev.2／dev.3／dev.4 候選保留在舊專案，不能當作新來源二進位。建置限制及驗收清單以[線上安裝與自動更新](ONLINE_INSTALL_AND_UPDATE_zh_TW.md)為準。

因此目前尚未達成「在任何地方下載安裝最新的純應用程式版」。下列流程是往後要完成並維持的標準作法。

## 一、固定的下載與保存位置

| 位置 | 用途 | 可放內容 |
| --- | --- | --- |
| MSH 原始碼 repository | 開發、review、測試、保存版本 | 程式、功能設定、測試、文件及 UI 素材；後續提交不得帶入模型或研究資料 |
| Public `MSH-Releases` | 一般使用者下載 | 已驗證的安裝檔、SHA-256、建置 manifest、版本說明、安裝指引、`latest.json` 及必要授權／對應來源交付資訊 |
| 使用者本機／受控外部儲存 | 研究、推論、訓練 | 自備模型、dataset、影像、標註、實驗與輸出；不傳入 Git 或公開 Release |

固定對外入口為 `MSH-Releases` 的 Releases 頁；新版附件與有效更新資訊尚未發布前，手動交付內部測試包。公開下載不應要求使用者取得私有原始碼或 GitHub token。
只有穩定版才設定為最新正式版本；候選版、未完成硬體驗收的測試版不得被當成正式最新版推送。
在首次穩定版發佈並確認 GitHub 的 Latest 指向後，才可把 `/releases/latest` 作為穩定版捷徑。

原始碼 repository 維持 Private，不因提供 APP 更新而公開研究歷史，也不改寫原有歷史。
`MSH-Releases` 只接收經審核的交付內容；必要的對應來源另提供乾淨、無研究資料與 Git 歷史的交付包，不把原庫整份搬入。

## 二、一般使用者第一次使用

1. 使用 Windows 10／11 64 位元電腦，開啟固定下載頁。
2. 閱讀該版本說明，下載正式版 `MSH_Setup_v<版本>_ONLINE.exe` 及同名 `.sha256`。
   安裝器優先選擇 NVIDIA GPU 套件，CPU 為備用；相容性以當版驗收結果為準。
   不要下載 GitHub 自動產生的 Source code ZIP 來當成可直接使用的安裝版。
3. 依發行頁提供的 SHA-256 核對檔案。發行者應優先提供已簽章安裝檔；未簽章測試版須明確標示。
   若來源、簽章或雜湊不符，停止安裝並回報，不為了安裝而關閉防護。
4. 關閉正在執行的 MSH，雙擊安裝檔，完成安裝並視需要建立桌面捷徑。
5. 從開始功能表或桌面啟動 MSH。沒有模型時應仍能開啟，AI 辨識會提示選擇模型。
6. 準備自己的相容模型，在 GUI 的模型選擇欄選取本機檔案，再執行辨識。
   目前每次啟動先保持未選模型，需重新選取；不會自動下載替代模型。
7. 模型建議存放在使用者自行管理、與應用程式安裝目錄分離的資料夾；模型與輸出另行備份。
8. 只有需要 Basler 取像時，才安裝對應相機介面的官方 pylon Runtime／驅動；GPU 版本另需相容 NVIDIA 驅動。
   相機、COM、Arduino、XY 與馬達依 B 地安全與驗收流程設定；安裝軟體不會自動燒錄韌體或校正硬體。

安裝版不要求使用者執行 `install_project.ps1`、`setup_gpu_env.ps1` 或 `update_project.ps1`。
這些腳本屬於開發／原始碼環境流程。

## 三、一般使用者往後更新

1. 在 MSH 使用「說明 → 檢查更新…」，或直接開啟固定下載頁。
2. 檢查更新內容與已知限制，確認後由 MSH 下載安裝檔並核對 SHA-256。
   無網路或 Private 存取失敗不阻擋既有版本；原始碼模式下載後不會替換 Git checkout。
3. 備份需保留的使用者資料與設定，正常結束 MSH 工作並斷開相機／馬達。
4. 下載完成後再次確認，MSH 正常退出才開啟安裝程式；不強制終止工作。維持相同 AppId、安裝範圍與帳號，讓一般後續版本沿用原應用程式身分。
5. 重開 MSH，確認版本、重新選取模型、測試常用功能；硬體版本相容性另外確認。
6. 若更新失敗，保留錯誤訊息及 `%LOCALAPPDATA%\MSH\msh.log`，回報版本、Windows 與 CPU／GPU 資訊。
   分享 log 前先移除個人路徑及敏感資訊；不把研究影像、模型或標註上傳到公開 Issue。

首次從舊的「內附模型」版本遷移時，不能假定覆蓋安裝會自動清除舊模型。
先備份所有需保留的使用者檔案，盤點舊安裝目錄後，使用舊版解除安裝程式移除舊應用程式，再安裝新版本。
不要手動大量刪除 `%LOCALAPPDATA%\MSH`、Documents 或研究資料夾。
一般後續新版的覆蓋升級也必須實測後，才能宣稱保留資料／設定成功。

## 四、模型訓練與更新走獨立流程

1. 在本機準備自己的資料、標註及初始模型，使用本專案保留的訓練工具。
2. 在本機驗證新模型，保存版本、相容性及評估結果；不要把這些研究產物加入 Git 或公開 Release。
3. 在已安裝的 MSH 選取新模型，檢查辨識功能與分類對應。
4. 只換相容模型時，不需要為此重新發佈 MSH；只有應用程式功能、介面或相容性處理改變時，才走新版安裝檔流程。
5. 需要跨機帶模型或資料時，使用另行核准的受控儲存／搬運方式，不使用應用程式的 Git 或公開下載頁。

目前訓練入口為避免下載 AMP 檢查模型而停用 AMP，可能增加顯存需求或降低速度；使用者提供的 checkpoint 權重會保留。
訓練能力保留在開發專案，不應把所有 CLI 訓練工具都宣稱成安裝版已提供的 GUI 功能；安裝版實際提供哪些入口，以該版驗收結果為準。

## 五、你往後每次修改到發佈的完整流程

### 1. 開工與定義版本範圍

- 在開發電腦執行「開始工作」，確認 branch、status、待辦與跨機工作狀態。
- 明確列出本版要包含的功能、已知限制及對應 source commit；不要把其他 branch 當成已整合。
- 核定新版本號，例如 `0.1.4` 僅是下一版示例；本文件不會替你升版。
- MSH 原始碼版本與正式 Release tag 必須一致；已發佈的安裝檔不覆寫，修正以新版本發佈。

### 2. 完成程式與軟體驗證

- 確認缺少模型時能開啟、選取自備模型後能辨識、清除模型後不繼續使用舊的辨識器。
- 在本機以合法可用的模型驗證實際相容性；模型檔、輸入與結果都不加入 Git。
- 執行適用自動測試、`python scripts/audit_application_files.py`、完整 diff 與敏感內容檢查。
- 僅明確 stage 本版檔案；來源資料的停止追蹤也要與對應程式／排除規則一起 review，不能只提交索引中的刪除。
- 不以單元測試成功代表實際模型推論、訓練、安裝或硬體驗證通過。

### 3. 保存原始碼與發行來源

- 使用者明確授權後才 commit／push；只推已核定的目的地，不猜測新 branch upstream。
- 需要合併其他功能或發行分支時，另取得明確 merge 授權並驗證整合結果。
- 先確認相機／馬達 GUI 與 B 地已燒錄韌體相容；目前固定轉速韌體與配套 GUI 仍有獨立整合、部署與驗收事項。
- 從乾淨、已審核的發行來源建立對應 `v<版本>` tag；tag 的建立與推送也須在授權範圍內。
- 「結束工作」可以依專案規則保存並推送已設定 upstream 的分支，但不會自動建立安裝檔或 GitHub Release。

### 4. 建置安裝版

依 [BUILD.md](release/BUILD.md) 與[線上安裝建置說明](ONLINE_INSTALL_AND_UPDATE_zh_TW.md)，分別使用乾淨且已驗證的 CPU/GPU 環境建置套件，再建立線上入口。以下為 CPU 套件範例：

```powershell
.\scripts\build_release.ps1 -Runtime cpu -PythonPath .\.venv312-cpu\Scripts\python.exe
```

正式模式要求乾淨來源與對應版本 tag，並禁止覆寫既有安裝檔。
內部測試可明確使用 `-Candidate`；其 `_CANDIDATE.exe` 不得發佈為正式版或寫入 `latest.json`。
不要繞過此腳本直接執行 Inno Setup。

建置產物應位於 `dist\release\v<版本>\`：

- `MSH_Setup_v<版本>_CPU.exe`
- `MSH_Setup_v<版本>_CPU.exe.sha256`
- `MSH_Setup_v<版本>_CPU.exe.build-manifest.json`

檢查 manifest：正確版本／source commit、`build_mode: release`、乾淨來源、正確 executable hash、
`model_distribution: user-supplied`、`bundled_models: []`、`bundled_research_data: false`。
還要實際檢查 payload，不能只相信 manifest 的宣告欄位。
依賴套件的發佈條款仍需檢閱；不內附模型不等於沒有軟體依賴的發佈義務。

### 5. 安裝與硬體驗收

- 在沒有 Python、Git、研究資料和模型的乾淨 Windows 帳號／測試機上安裝並啟動。
- 驗證自備模型選取、實際辨識、輸出路徑、關閉／重開、重複啟動、解除安裝及資料保留。
- 實測舊內附模型版遷移及一般新版覆蓋升級；不把舊安裝目錄殘留權重誤認為新包提供的內容。
- 硬體功能需在 B 地取得當次操作授權後，驗證 Basler、COM、韌體相容性、XY、停止／釋放與掃描。
- 依本版要宣稱的功能完成驗收；未驗收項目記錄限制，不能把測試版當作完整硬體正式版。

### 6. 發佈可下載的新版本

以下建置、交付清單審核與同庫發行已可由[自動建置與發行流程](AUTOMATED_RELEASE_zh_TW.md)處理，無須手動搬檔。
先 prepare-release 產生私人產物，再以 publish 明確批准該次產物；候選版不能公開發布。

- 完成發行審查並取得公開發佈授權後，在同一個 `MSH-Releases` repository 建立該版本的 Release 草稿。
- 只上傳核准的安裝檔、`.sha256`、建置 manifest、必要授權／來源 ZIP 與使用說明；不附模型、研究資料、log、開發環境或原始碼歷史。
- 版本說明列出更新內容、模型自備要求、最低環境、測試證據、硬體限制及是否簽章。
- 審查草稿、確認附件及下載目的地後，發佈正式版；未通過的版本維持內部候選，不更新穩定版指向。
- 從未登入的瀏覽器／另一台電腦下載，驗證檔案可用、SHA-256 正確且安裝成功。

### 7. 最後才更新通知資訊

- 發行程式依已核對的交付清單，最後才在公開發佈 repository 更新根目錄 `latest.json`；`release/latest.example.json` 僅供格式參考。
- 填入真實版本、更新內容、已可下載的安裝檔網址、Release 頁、SHA-256 及日期；不得保留範例值。
- 安裝檔可下載且驗證完成後，才發布更新資訊；此步驟會向既有使用者宣布新版，因此也需在發佈授權範圍內。
- 從舊版按「檢查更新」，驗證顯示的新版本、下載網址、雜湊及完整升級流程。
- 未發佈新版時，程式碼可以已上傳，但使用者看到的最新可安裝版仍是上一個正式 Release。

### 8. 收尾與跨機續作

- 記錄版本、commit、tag、Release 網址、安裝檔雜湊與各項驗證結果。
- 保留前版安裝檔與本機研究資料備份，不刪除原檔來讓 Git 看起來乾淨。
- 更新當前工作流及未完成事項；跨機前到 `My-Codex-Profile` 按既有流程保存 Global work state。
- 若新版有問題，先停止推薦該版本並決定修正版／回復方案；不覆寫已發行的二進位檔，也不自動降版更新。

## 六、目前到第一次可直接下載，還差哪些事項

1. 核定發行範圍、版本及必要分支整合；確認軟體／韌體相容性。
2. 審查本次修改、保存原始碼與核定發行 tag。
3. 完成套件發佈條款檢閱，建置不含模型／研究資料的新安裝檔。
4. 完成乾淨電腦安裝、舊版遷移、模型與必要 B 地功能驗證。
5. 核准並發佈到 `MSH-Releases` 的 Releases，再在該庫的 main 根目錄建立可用的 `latest.json`。
6. 從外部下載並走完更新流程，才宣布「可隨時下載最新正式 MSH」。

這份文件僅建立流程，沒有執行 commit、push、merge、tag、硬體操作或公開發佈。
